# AI Text Polisher 规格说明

## 概述
AI Text Polisher 是一个纯前端网页应用，用于根据用户选择的场景预设，对用户输入的文本进行改写润色。用户将原始文本贴入左侧编辑区，从顶部选择 6 个预设中的一个，点击润色按钮后，右侧显示 AI 生成的改写结果。该产品范围非常明确：不包含注册登录、不包含协作、不包含 CMS，也不包含单用户文本润色之外的其他工作流。

应用使用 DeepSeek 生成润色结果，并且必须提供一个单页、轻量、适合快速改写和复制输出的体验。

## 用户体验目标
- 让核心操作一目了然：贴文本、选预设、润色、复制。
- 保持界面集中在一个页面内，并清晰区分输入与输出。
- 请求进行中时给出即时反馈。
- 当 API 请求失败时，优雅地显示友好提示。
- 单次润色请求强制限制为 3000 字符。

## 功能需求

### FR-1 单页文本润色流程
应用必须提供一个页面，让用户可以输入原始文本、选择预设、触发润色，并查看改写结果，整个过程无需页面跳转。

**验收标准**
- 页面显示原始文本输入区。
- 页面显示润色结果输出区。
- 页面包含润色按钮。
- 完成工作流不需要路由切换。

### FR-2 场景预设选择
应用必须提供且仅提供 6 个场景预设，并允许用户在润色前选择一个预设。

**预设列表**
- 学术润色
- 商务邮件
- 社交媒体
- 技术文档
- 创意写作
- 翻译优化

**验收标准**
- UI 中恰好有 6 个可选预设。
- 任意时刻只能选中一个预设。
- 选中的预设会参与 AI 请求构建。
- 用户提交请求前即可看到预设列表。

### FR-3 学术润色行为
当用户选择学术润色时，生成结果必须使用正式学术语气，去掉口语化表达，并保持原意不变。

**验收标准**
- 提示词要求模型使用正式学术语言。
- 提示词要求模型不要改变原意。
- 输出应更像学术文本，而不是口语表达。

### FR-4 商务邮件行为
当用户选择商务邮件时，生成结果必须使用专业商务语气、结构清晰，并在开头包含问候、结尾包含礼貌结束语。

**验收标准**
- 提示词要求专业商务邮件风格。
- 输出包含合适的称呼或问候语。
- 输出包含礼貌结束语。
- 结构清楚，符合邮件表达习惯。

### FR-5 社交媒体行为
当用户选择社交媒体时，生成结果必须轻松活泼，可适当使用 emoji，并在可能情况下控制在 280 个中文字符以内。

**验收标准**
- 提示词要求轻松活泼的社交风格。
- 提示词允许 emoji 使用。
- 输出目标长度不超过 280 个中文字符。
- 即使模型返回少于 280 字符，UI 也不能阻断流程。

### FR-6 技术文档行为
当用户选择技术文档时，生成结果必须保持术语准确，偏向被动语态，必要时使用编号步骤，并保留代码格式。

**验收标准**
- 提示词要求准确的技术术语。
- 当源文本包含流程时，提示词要求使用编号步骤。
- 提示词保留代码块和行内代码格式。
- 输出应符合技术文档风格。

### FR-7 创意写作行为
当用户选择创意写作时，生成结果必须强调文学表达，并使用比喻、排比、拟人等修辞手法。

**验收标准**
- 提示词要求创意文学风格。
- 提示词鼓励使用修辞手法。
- 输出应比输入更具表现力。

### FR-8 翻译优化行为
当用户选择翻译优化时，应用必须双向提升翻译质量：中文输入应生成地道英文，英文输入应生成流畅中文，而不是逐字直译。

**验收标准**
- 提示词要求模型自动判断源语言。
- 提示词要求以目标语言输出地道表达。
- 输出避免机械式直译。

### FR-9 加载状态
应用必须在润色请求处理中显示加载提示。

**验收标准**
- 润色按钮或相邻状态区域显示“润色中...”之类的文案。
- 加载提示在提交后、结果返回前出现。
- 请求完成或失败后，加载提示消失。

### FR-10 友好错误处理
如果 API 请求失败，应用必须显示对用户友好的提示信息。

**验收标准**
- 网络失败或服务端失败不会导致页面崩溃。
- 用户能看到友好的错误提示。
- 提示信息不暴露原始堆栈或低层 API 细节。

### FR-11 复制结果
应用必须支持一键复制润色结果。

**验收标准**
- 当结果存在时，界面提供复制按钮。
- 点击复制后，结果文本进入剪贴板。
- 复制完成后，用户能获得成功反馈。

### FR-12 文本长度限制
应用必须阻止单次润色请求的源文本超过 3000 字符。

**验收标准**
- 输入区明确限制或提示 3000 字符上限。
- 用户不能提交超过 3000 字符的文本。
- 达到上限时，界面给出清晰反馈。

### FR-13 DeepSeek 模型选择
应用必须使用 DeepSeek 的 deepseek-chat 模型进行润色请求。

**验收标准**
- 请求载荷中明确指定 deepseek-chat。
- 模型选择是固定的，不能由用户更改。

### FR-14 开发环境 API 路由
开发环境必须使用 Vite 代理，让 `/api/*` 请求转发到 `https://api.deepseek.com/*`。

**验收标准**
- 开发请求使用 `/api/*` 路径。
- 代理会把请求转发到 DeepSeek 接口。
- 前端组件中不直接写死 DeepSeek 的绝对地址。

### FR-15 基于环境变量的 API Key
应用必须从 `VITE_DEEPSEEK_API_KEY` 读取 API Key，且绝不能在源码中硬编码密钥。

**验收标准**
- API Key 从环境变量读取。
- 源文件中不出现任何 API 密钥。
- 缺少密钥时，界面给出清晰友好的提示。

## 非功能需求
- 应用必须保持纯前端单页应用形态。
- 界面必须轻量、清晰、易于浏览。
- 代码库必须保持 UI、API、提示词配置分离。
- 实现必须兼容宪法中锁定的技术栈。

## 用户场景

### 场景 1：学术润色
用户贴入论文草稿中的一段文字，选择学术润色，点击润色，等待加载状态后，得到一段保留原意、可直接复制的学术化文本。

### 场景 2：商务邮件改写
用户贴入一段非正式的内部说明，选择商务邮件，得到结构清晰、带问候和结尾的邮件文本，可直接发送或继续编辑。

### 场景 3：社交媒体文案
用户贴入一段简短公告，选择社交媒体，得到一段简洁、生动的文案，符合长度预期，复制后即可发布。

### 场景 4：技术文档整理
用户贴入包含代码片段的步骤说明，选择技术文档，得到更清晰的文档风格改写，保留代码格式与步骤结构。

### 场景 5：创意改写
用户贴入一段平实描述，选择创意写作，得到更有画面感、带修辞的版本。

### 场景 6：翻译优化
用户贴入中英混合或直译文本，选择翻译优化，得到更自然、符合目标语言习惯的结果。

## 成功标准
- 用户可以在一个页面内完成输入、选场景、润色和复制全流程。
- 6 个预设全部可用，并产生不同的提示词行为。
- 加载状态和错误状态清晰可见。
- 3000 字符限制有效。
- 结果可以一键复制。
- 应用使用锁定的技术栈和固定的 DeepSeek 模型。
- 提示词修改不需要改 UI 代码。

## 假设
- 应用面向桌面浏览器和现代移动浏览器。
- 润色结果以纯文本或安全渲染文本的形式展示，不是可编辑文档。
- 输出可以基于不同预设多次重新生成，但同一时刻只需要处理一个请求。
- 复制反馈可以用 toast、内联提示或按钮状态变化来展示。

## 范围边界
### 范围内
- 文本输入与输出
- 6 个预设选择
- AI 润色请求与响应处理
- 结果复制
- 加载与错误状态
- 字符限制控制

### 范围外
- 用户账户
- 协作功能
- 历史记录保存
- CMS 功能
- 多页面路由
- 服务端持久化存储
- 通用文档编辑
